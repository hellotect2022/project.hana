# qa-code-review

## 목적
일관된 기준으로 코드/문서/설정/보안을 검증하고 PASS/WARNING/FAIL을 판정한다.

## 사용 시점
AGENT 작업 보고서 제출 후, 초기 세팅 검증, 변경사항 검증 시. qa-code-reviewer 전용.

## 적용 대상
전체 프로젝트(검증 전용, 수정 금지).

## 절차
1. 검증 대상과 파일 목록을 확정한다.
2. 구조/기능/테스트/문서 정합성/보안을 점검한다.
3. 필요한 검증 명령만 실행한다(`gradlew test`, `gradlew build`, `tsc --noEmit` 등).
4. 근거(파일·라인)와 함께 QA 보고서를 작성한다.
5. FAIL/WARNING이면 수정 요청 대상 AGENT를 지정한다.

## QA 보고서 양식 (qa/reports/)
```
# QA 검증 보고서
## 1. 검증 대상
## 2. 검증 파일
## 3. 전체 판단 (PASS/WARNING/FAIL)
## 4. 핵심 문제
## 5. 코드 구조 검증 (구조/책임 분리/중복/확장성)
## 6. 기능 검증 (요구사항/API 흐름/데이터 흐름/예외 처리)
## 7. 테스트 검증 (존재/누락/수동 필요)
## 8. 문서 정합성 (문서-코드/API 명세/누락 문서)
## 9. 보안·설정 (민감정보/환경변수/의존성)
## 10. 수정 요청 대상 AGENT
## 11. 수정 요청 내용
## 12. 재검증 필요 여부
```

## 체크리스트
- [ ] 리액티브(gateway/event)에서 블로킹 호출 없는가
- [ ] 트랜잭션/리소스(커넥션·스트림) 정리되는가
- [ ] 예외 처리·검증(@Valid) 누락 없는가
- [ ] 백엔드 API ↔ 프론트 services 계약 일치하는가
- [ ] 민감정보(비밀번호/JWT 시크릿) 노출 없는가
- [ ] 문서·API 명세가 구현과 일치하는가

## 판정 처리
- PASS: 수정 없음, 보고서 저장, 다음 Loop 가능.
- WARNING: 위험도 기록, 사용자 판단 대기, 승인 전 수정 금지.
- FAIL: 다음 Loop 금지, 수정 승인 요청서 작성, 승인 후 수정 → 재검증.

## 금지 사항
- 코드/문서/설정 수정(검증자는 수정자가 아니다)
- 근거 없는 판정

## 출력 형식
QA 검증 보고서 Markdown.
